# Source Authority and Conflict Handling

## Source handling rules
1. Record source identity, version/date when present, and whether it is a signed agreement, approved requirement, working draft, design prototype, or generated artifact.
2. Use explicitly confirmed user decisions and signed/approved agreement terms as primary evidence for current direction, while flagging any contractual inconsistency for review.
3. Do not assume a document is authoritative only because its filename or upload date is newer.
4. Requirements documents describe intended behavior; they do not prove implementation.
5. Prototype HTML and screenshots show interface ideas and sample data; they do not prove persistence, secure authorization, or correct calculations.
6. Generated prompts, candidate schema files, and conceptual diagrams are supporting material, not automatically approved requirements.
7. When two sources disagree, document both statements, link both sources, state the impact, and mark the decision owner/action needed. Do not silently reconcile.

## Product naming
Current user-confirmed product/system name: **RouteX: Profitability Analysis System**. Older source documents may use longer names; preserve originals in the canonical archive and use the current name in new knowledge-base prose.

## Mirrors and traceability
Where a knowledge-base note mirrors a source section, add a `Mirrors:` note naming the source document and section. Update the source and mirrored note together when the source is changed. Canonical source copies must never be edited in place.
